# Stage Memory — Domain Design

Observation diary for this stage. Hand-maintained narrative.

## Interpretations

- 2026-10-18 — This stage is where six questions deferred since Intent Capture and Requirements Analysis finally land: the teacher-vs-teacher privacy boundary, the FeeCycle redesign, deletion dispositions per table, academic-record retention, the subscription absorb mechanism, and the concurrent-edit rule. None of them is a component-boundary question in the stage's usual sense; all six are structural decisions that the component catalogue then has to express. So the order here is: decide the six, then draw the components around what they imply — not the reverse.
- 2026-10-18 — The stage file is explicit that components are **code you write**, not infrastructure, and that deployment topology belongs to Units Generation. Entity capture is ownership-and-shape only: which component owns what, identifiers, attribute names, cross-component references. Types, constraints and cardinality belong to Functional Design. Keeping to that line matters here because the fee ledger invites premature schema detail.

## Deviations

- 2026-10-18 — Running autonomously at the user's instruction, so the six questions went to a dispatched architect rather than to the user. That is the user's explicit delegation, not an assumption of autonomy — and the stage's own approval gate still returns to them.

## Tradeoffs

- 2026-10-18 — Dispatched one specialist with all six questions rather than six specialists with one each. They interact: the deletion dispositions depend on the ledger shape, the retention periods depend on the dispositions, and the concurrency rule depends on whether the ledger is append-only. Six independent answers would have had to be reconciled afterwards, and the reconciliation is where the real design is.
- 2026-10-18 — The architect found a defect in the team's **affirmed** practices, not in a draft: `team.md` records the Hypothesis invariant as `charged - received - forgiven == outstanding`, which omits carry-forward — in the same sentence that lists carry-forwards among the operations the invariant covers. It would fail on its first carry-forward, and it predates the credit concept entirely. Verified against the file before accepting. This is a permanent rule, so it goes through the learnings gate rather than a direct edit. The corrected three-part form is recorded in `decisions.md` ADR-002.
- 2026-10-18 — The strongest piece of the architect's reasoning was on Q1, and it reframed the problem: the teacher-vs-teacher leak is not a missing RLS policy but a question of **what a teacher-facing endpoint may be keyed by**. The existing three-layer boundary separates *writers* (profile vs enrollment), and here both teachers write enrollment-shaped data in the same tables, so that boundary cannot see the leak. If no teacher-facing route accepts or returns an account id, the leak has no address to travel to. That turns a vague "scope it properly" into one mechanically checkable invariant.
- 2026-10-18 — Q6 found a failure mode I would not have: a roster queued offline at 10:15, a correction made from another device at 11:00, and the queue arriving at 11:40 silently reinstating the stale mark — with the correction history then faithfully recording a change the teacher never made, which is worse than no history because it looks authoritative. Per-field last-write-wins cannot save it, because AC3.1.5 requires the roster to be one atomic write, so field granularity does not exist. Hence refuse-and-tell rather than merge.
- 2026-10-18 — Applied ADR-006's two required upstream amendments. `FR11.4` now splits concurrency by write path rather than stating one rule, and `NFR5.1` carries four queue states rather than three. Added `FR11.5` unprompted: `conflicted` is a state the client can reach, and a reachable state with no screen is a gap that surfaces as a dead end in Construction. `A9` was narrowed to the interactive path — the original assumption ("simultaneous editing is rare") is false for the queued path by construction, since the delay between composing and sending is exactly what makes a conflict plausible there.
- 2026-10-18 — The architecture reviewer returned READY with one Major and one Minor finding. The Major one was real and I had missed it: ADR-002's *corrected* invariant was still wrong, failing on the very overpayment case the correction existed to fix. Cause: `receipt` records only the applied part of a payment, so money arriving as `credit_grant` never reached the received side. Cash in is `receipt + credit_grant`.
- 2026-10-18 — The reviewer's prescribed fix was wrong, though. Adding `credit_grant` with a `+` to the left side as it suggested fails cases 2, 3, 7 and 8. Verifying before applying caught this; applying the suggested patch would have replaced one wrong invariant with another, and the next reader would have trusted it more because it had been through review.
- 2026-10-18 — Working the algebra turned up a **second defect the reviewer did not find**: `carry_forward` was one-sided, so a carried debt sat in the old cycle's outstanding *and* the new cycle's carried-in. An enrollment carrying 1000 into a second 1000 charge read 2500 owed against a true 1500. Fixed by making carry two-sided — `carried_out` relieves the origin — after which the two kinds cancel at enrollment level, which is correct: moving a debt between periods is not an economic event.
- 2026-10-18 — The final form was checked against twelve worked cases and then 20,000 randomized enrollment histories, zero failures. Asserting an invariant I had already got wrong twice was not good enough, particularly as the team's practice makes this identity the property-based test behind 100% branch coverage on the money module.
- 2026-10-18 — Took the Minor finding: `LedgerEntry.amount`, `PaymentClaim.claimed_amount` and `PaymentVerification.approved_amount` now carry explicit Money-type notes.
- 2026-10-18 — A second, independent reviewer returned NOT-READY with two Major findings the first reviewer missed entirely. Dispatching fresh eyes rather than re-asking the same reviewer was what surfaced them: the first review had confirmed the areas it was pointed at and stopped there.
- 2026-10-18 — The worse of the two: ADR-003 cited a "full disposition table in components.md" that was never written. Only 2 of 24 entities had a stated disposition, so Governance's core deliverable was undecided for 22 tables and the claim "the privacy policy is now generatable" was false — the claim that unblocks the release-blocking RC-4 and RC-5. A citation to content that does not exist is worse than an admitted gap, because it closes the question in the reader's mind.
- 2026-10-18 — The other: `Batch.default_fee` and `Enrollment.fee_amount` are the fee anchors the whole model charges against, and neither owning component declared any Money dependency. The import-boundary check would not have caught it — it blocks raw `decimal` imports outside `app/money`, not a bare untyped `Numeric` column. The enforcement mechanism had a hole exactly where the money model begins.
- 2026-10-18 — The dispatched compliance specialist resolved the central tension well: `Enrollment` is anonymize-in-place rather than retain, because it is the only path from an Account to any academic or financial row, so severing its two account columns de-identifies attendance, marks, fee cycles, claims and reminders in one write. That is what lets the downstream rows be honestly retained — after the sever they link to no living data subject. Verified the "only path" claim against all eleven entities carrying an account id before accepting it.
- 2026-10-18 — It returned five undecided items and I settled four, because each changes what the release-blocking deletion test asserts. U1 (multi-role accounts) was the important one: FR11.1 and FR11.2 are both written as though an account holds exactly one role, but role is a per-request lens, so a tutor who is also a parent is ordinary here. Resolution is apply-every-matching-predicate, most-destructive-wins per column. U3 needed a new column, `relink_blocked_at`: without it an erased student whose number returns is silently reattached to their own erased history, which defeats the erasure invisibly.
- 2026-10-18 — Left U2 open rather than inventing an answer: whether `PaymentClaim.transaction_id` survives the claimant's deletion turns on how long a teacher actually needs an external payment reference to settle a dispute, which is a product and legal judgement nobody has made. It is the last external re-identification path, so it matters, but guessing it would be worse than naming it.

## Open questions

- 2026-10-18 — Still unowned and external: the SMS gateway vendor, the Play Console account type, the teacher-onboarding mechanism for closed testing, and the uncosted web surface the external deletion route needs.
- 2026-10-18 — Carried in from Refined Mockups: four screens have no artboard, including the walking-skeleton OTP sign-in; tablet and landscape layouts are committed but undrawn.
- 2026-10-18 — A third reviewer verified the fixes and returned READY: 24/24 entities in both disposition tables, all 20 graph edges symmetric and acyclic after the Money additions, all five money-shaped fields annotated with no sixth left behind, `relink_blocked_at` present in both the entity list and the summary table. Its one Minor finding was a good catch on my wording rather than on the design: I had stated U1's rule as a column-priority comparison when what actually produces the right answer is row-set separation — teacher-authored rows and the person's own rows are different rows. The priority order is only a tie-break for a same-row conflict no entity currently produces. Rewritten so a future reader does not inherit an overstated rule.
- 2026-10-18 — Three reviewers over one stage was the right cost here. The first confirmed what it was pointed at; the second, briefed away from that ground and toward unprobed areas, found both Major defects; the third caught an overstatement introduced by the fixes themselves. The pattern worth keeping is that a fresh reviewer with a different brief finds more than a second pass from the same one.
