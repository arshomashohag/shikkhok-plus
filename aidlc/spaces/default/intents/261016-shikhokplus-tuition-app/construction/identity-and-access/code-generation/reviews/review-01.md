| R-01 | Critical | app/audit/log.py > `write_audit` | Reproduced against a real PostgreSQL 16 container (not a mock): when the audit INSERT fails with a genuine database error (e.g. a constraint violation), SQLAlchemy 2.x invalidates the underlying DBAPI transaction as part of raising the error. `write_audit` catches `SQLAlchemyError` and only logs CRITICAL, so the caller (`app/auth/otp.py::issue`, `::verify`, `app/auth/tokens.py::rotate`) proceeds to call `session.commit()` believing the operation succeeded. That commit does not raise, but it commits nothing, because the transaction was already rolled back at the connection level before `write_audit` returned. In a minimal reproduction mirroring `otp.issue()`'s shape (insert the real row, then a failing audit insert, then commit), the real row vanished: `otp_request` had 0 rows after the "successful" commit. This is not "fails open" as claimed in the module docstring and in `code-summary.md` §B ("the authentication must not fail because its record did") — it is silent data loss: the OTP is issued to the user (the SMS is sent) but the server holds no record it exists, so the subsequent verify will find no row and refuse every code the user was just sent. The same mechanism can silently discard a successful verify's `consumed_at` update or a refresh rotation. The project's own `tests/audit/test_audit_log.py::test_the_audit_write_fails_open_rather_than_raising` cannot catch this: it monkeypatches `session.execute` to raise directly from Python, which never touches a real connection and therefore never poisons a transaction — it only proves the exception is caught, not that the surrounding work survives. No test in `tests/auth/test_otp.py` or `tests/auth/test_tokens.py` exercises a real audit-write failure inside `issue`/`verify`/`rotate` against the real Postgres fixture. This is exactly the class of "wrong version reads as more security-conscious" defect code-summary.md §B set out to hunt, and it was not found because the defect was never actually injected at the database level — only at the Python mock level. | Make the audit write and the primary write independently durable under failure, e.g. by writing the audit row in its own sub-transaction/savepoint (mirroring the pattern already used for BR2.7's existence oracle) so a failed audit insert cannot roll back the OTP/verify/rotation state, or by moving the audit write to happen after the primary `session.commit()` on its own connection. Add an integration test that injects a real constraint violation (not a mocked `execute`) inside `otp.issue`/`otp.verify`/`tokens.rotate` and asserts the primary row survives the subsequent commit. | New |

| R-03 | Minor | app/auth/ceilings.py > `CeilingChecker._release` | `_release` issues `UPDATE rate_limit_counter SET count = count - 1 WHERE ...` with no `WHERE count > 0` guard and no check that the row it is decrementing is still the one it incremented (no optimistic check on a version or on the exact count value read). I attempted to reproduce a negative-counter or over-admission race by running 5 threads concurrently against a counter pinned at its limit (3) against a real Postgres container; Postgres's row lock on the `ON CONFLICT DO UPDATE` serialized the attempts and the counter settled back to exactly the pre-breach value (3) with every request refused — so this did not reproduce the feared defect under the scenario I could construct in the time available. It remains true that the decrement is a separate statement/transaction from the increment it undoes, which is a less direct mechanism than a single atomic statement, and the existing `test_concurrent_increments_at_the_boundary_admit_exactly_one` test drives its "concurrent" sessions through a sequential Python loop rather than true thread/process concurrency, so the test's name overstates what it exercises. | Either strengthen `test_concurrent_increments_at_the_boundary_admit_exactly_one` to use real concurrent threads/connections (as I did to probe this), or note in the test's docstring that it exercises sequential interleaving only, so a future reader does not treat it as proof against a true race. | New |

### Summary

The core cryptographic, authorization-boundary, and ceiling-cascade controls hold up under direct adversarial reproduction against a real PostgreSQL instance, and several of the specific concerns raised in the dispatch brief (BR3.2's RLS policy, BR4.1's family invalidation, the BR2.5 concurrent-release race) did not reproduce as defects. The blocking issue is the audit log's own fail-open claim: it is not actually fail-open against a real database failure, it is silent data loss of the primary authentication state, and the project's own verification methodology (inject the defect, record what fires) never injected this specific defect at the database level — it was only ever exercised through a mock that cannot poison a transaction. Combined with the disclosed-but-real absence of any Compose UI, which the team's own Walking Skeleton practice requires for this checkpoint, the Bolt is not ready to pass its skeleton checkpoint as submitted.
