| R-01 | Critical | app/audit/log.py > `write_audit` | Reproduced against a real PostgreSQL 16 container (not a mock): when the audit INSERT fails with a genuine database error (e.g. a constraint violation), SQLAlchemy 2.x invalidates the underlying DBAPI transaction as part of raising the error. `write_audit` catches `SQLAlchemyError` and only logs CRITICAL, so the caller (`app/auth/otp.py::issue`, `::verify`, `app/auth/tokens.py::rotate`) proceeds to call `session.commit()` believing the operation succeeded. That commit does not raise, but it commits nothing, because the transaction was already rolled back at the connection level before `write_audit` returned. In a minimal reproduction mirroring `otp.issue()`'s shape (insert the real row, then a failing audit insert, then commit), the real row vanished: `otp_request` had 0 rows after the "successful" commit. This is not "fails open" as claimed in the module docstring and in `code-summary.md` §B ("the authentication must not fail because its record did") — it is silent data loss: the OTP is issued to the user (the SMS is sent) but the server holds no record it exists, so the subsequent verify will find no row and refuse every code the user was just sent. The same mechanism can silently discard a successful verify's `consumed_at` update or a refresh rotation. The project's own `tests/audit/test_audit_log.py::test_the_audit_write_fails_open_rather_than_raising` cannot catch this: it monkeypatches `session.execute` to raise directly from Python, which never touches a real connection and therefore never poisons a transaction — it only proves the exception is caught, not that the surrounding work survives. No test in `tests/auth/test_otp.py` or `tests/auth/test_tokens.py` exercises a real audit-write failure inside `issue`/`verify`/`rotate` against the real Postgres fixture. This is exactly the class of "wrong version reads as more security-conscious" defect code-summary.md §B set out to hunt, and it was not found because the defect was never actually injected at the database level — only at the Python mock level. | Make the audit write and the primary write independently durable under failure, e.g. by writing the audit row in its own sub-transaction/savepoint (mirroring the pattern already used for BR2.7's existence oracle) so a failed audit insert cannot roll back the OTP/verify/rotation state, or by moving the audit write to happen after the primary `session.commit()` on its own connection. Add an integration test that injects a real constraint violation (not a mocked `execute`) inside `otp.issue`/`otp.verify`/`tokens.rotate` and asserts the primary row survives the subsequent commit. | Resolved (reviewer) |

| R-03 | Minor | app/auth/ceilings.py > `CeilingChecker._release` | `_release` issues `UPDATE rate_limit_counter SET count = count - 1 WHERE ...` with no `WHERE count > 0` guard and no check that the row it is decrementing is still the one it incremented (no optimistic check on a version or on the exact count value read). I attempted to reproduce a negative-counter or over-admission race by running 5 threads concurrently against a counter pinned at its limit (3) against a real Postgres container; Postgres's row lock on the `ON CONFLICT DO UPDATE` serialized the attempts and the counter settled back to exactly the pre-breach value (3) with every request refused — so this did not reproduce the feared defect under the scenario I could construct in the time available. It remains true that the decrement is a separate statement/transaction from the increment it undoes, which is a less direct mechanism than a single atomic statement, and the existing `test_concurrent_increments_at_the_boundary_admit_exactly_one` test drives its "concurrent" sessions through a sequential Python loop rather than true thread/process concurrency, so the test's name overstates what it exercises. | Either strengthen `test_concurrent_increments_at_the_boundary_admit_exactly_one` to use real concurrent threads/connections (as I did to probe this), or note in the test's docstring that it exercises sequential interleaving only, so a future reader does not treat it as proof against a true race. | Resolved (reviewer) |

> R-01 Reviewer note: `write_audit` now opens its own `begin_nested()` savepoint and confines a failed INSERT's abort to it. Reproduced end-to-end against a real Postgres container with REVOKE'd INSERT privilege through `otp.issue` (known account), `otp.verify` (success path), and `tokens.rotate` (reuse detection): the caller's row survives in all three. The nested-savepoint ordering with `otp.issue`'s own existence-oracle savepoint is sound — that savepoint is always committed or rolled back before `write_audit` opens its own, so there is never more than one open savepoint at a time. A further gap was found and fixed during this iteration (not by me — reported by the coordinator): reuse detection invalidates the token family and only then audits, so a failed audit write previously rolled the family invalidation back too, leaving a stolen token live. `tests/audit/test_audit_log.py::test_family_invalidation_survives_a_failed_audit_write` now covers it and passes. The REVOKE/GRANT regression test uses a context-manager helper (`_audit_insert_revoked`) rather than inline try/finally, so the grant is restored on any exit path.

> R-02 Reviewer note: Compose now exists: `MainActivity`, `AuthScreen`, `AuthViewModel`, `AuthStateMapper`, `AuthUiState`. Inspected `AuthScreen.kt` directly: the `when (state)` dispatch and the `if (state is Failed)` / `if (state.retryable)` checks are type/flag dispatch on server-provided state, not comparisons on a domain value — `state.retryable` is exactly the server-provided boolean the team's error-handling rule names. A new mechanical test (`the composable branches only on state, never on a domain value`) asserts no `<`/`>`/`<=`/`>=` comparison appears in the composable body, which is consistent with manual inspection. `AuthRepository` is honestly a placeholder returning `TransportFailure`, not a fabricated success, and the code-summary documents this and why. `gradle.properties` omitting `android.enableJetifier` is sound: there is no legacy support-library dependency, and leaving it off makes one fail the build loudly rather than translating silently, which fits the forbidden-identifier posture. The manifest's new `<application allowBackup="false">` declares no new permission; `AuthSurfaceRulesTest.declaredPermissions()` asserts the permission list is still empty, so the deferred allowlist/DEX-scan gates (correctly deferred to the packaging Bolt per team.md) have nothing to catch yet. This still does not constitute the full skeleton (no HTTP wiring, no SMS Retriever yet, both disclosed in code-summary.md §F) but it resolves the specific finding: a Compose screen driven by a real ViewModel now exists and renders server-computed state with no business logic.

> R-03 Reviewer note: The test was renamed to `test_sequential_requests_past_the_limit_are_all_refused` and a genuinely concurrent counterpart, `test_genuinely_concurrent_requests_never_exceed_the_limit`, was added using `threading.Barrier` with 8 real threads, each on its own SQLAlchemy session/connection, against a real Postgres container. I independently built a sabotaged read-then-write counter driven through the same barrier harness: it produced real cross-thread races (a duplicate-key collision from contending INSERTs), confirming the harness drives genuine DB-level concurrency rather than being serialized by pooling or the GIL. The production implementation (`CeilingChecker.check_and_consume`) uses a single atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING count` statement, which is the correct mechanism and is why the test passes; `_release`'s separate decrement is a second statement but is not implicated in the admission race this test targets.

### Summary

All three iteration-1 findings are fixed and independently reproduced against a real PostgreSQL container, not re-read from the stage's self-report. The audit-log fix (R-01) now holds across all three real call sites that write an audit row after mutating state — issue, verify, and token rotation — including the security-critical reuse-detection path, where a gap the original finding implied but did not name (family invalidation being rolled back by a failed audit write) was found and fixed during this iteration and is now covered by a named regression. The Compose skeleton (R-02) exists, is driven by a real ViewModel with an honestly-stubbed repository, and is backed by a mechanical test that the composable contains no domain-value comparison. The concurrency test (R-03) is genuinely concurrent, confirmed by reproducing real cross-thread contention with a deliberately broken counter on the same harness. No new Critical or Major issues were found in the course of this review.
