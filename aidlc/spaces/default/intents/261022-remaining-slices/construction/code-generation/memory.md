## Deviations
<!-- example: 2026-05-29T10:14:32Z — skipped the optional caching layer the stage prose suggested; the dataset is small enough that it adds risk -->
- 2026-10-23 (D2) — The plan's Step 6 named three new response fields while Step 12 required `isRemovable` to be **read from the server**, and no field carried it. The plan as written could only have been satisfied by a client-side derivation, which BR3.1 forbids for a concrete reason: `remove_enrollment` tests two conditions and the roster row carries only the first, so a derivation would offer removal on an erased seat whose decisions both read `pending`. Added `is_removable` as a fourth field rather than implementing Step 12 incorrectly. A plan can be internally inconsistent in a way that is only visible from the code; the check is whether the data the later step reads actually exists.
- 2026-10-23 (D2) — Exporting the guardian-state predicate publicly from `app/batches/service.py` failed `test_every_public_function_takes_a_lens`, correctly: a public function in that module taking no lens cannot be scoped by one. The fix was not to exempt it but to stop crossing the boundary with a predicate — `add_enrollment` now returns a `RosterRow` built by the same private `_roster_row` the roster uses, so the data crosses as a row and the API maps one shape. A gate refusing a convenience is usually describing a better design.

- 2026-10-24 (D3) — The security design specifies the collection-number allowlist as an equality against a **one**-element set and the built application has three: the downward payment-destination route the design named, plus `GET` and `POST /v1/batches`, which are the teacher reading and writing their own number on their own batch. The design predates D2's batch routes. Widening the allowlist silently would have left the next reader unable to tell which document was current, so the set is annotated with why each entry is there and the distinction the gate cannot make is asserted separately: the downward route must resolve **no** teacher lens, the owner routes **only** one. A design document written against an older schema is stale rather than wrong, and the difference belongs in the code.
- 2026-10-24 (D3) — Step 43's freshness check is specified as "not cron, so the two do not share a failure mode". Implemented as a `Restart=always` systemd service, and then the comment I first wrote claimed it survived an instance replacement — which is false, because `user_data.sh.tftpl` writes both and a replacement reinstalls both. Corrected to state what it does cover (a broken crontab, a dead daemon, a nightly error) and what it does not. Writing the honest bound was harder than writing the mechanism, and the first version was the kind of claim this project's memory is full of.

## Tradeoffs

- 2026-10-23 (D2) — `tests/test_named_test_manifest.py` parsed Python ASTs only, and NFR23.6's Back-after-child-switch test is Kotlin. A manifest that can hold only Python entries would have silently dropped the single obligation most at risk of becoming a review note — the one no server-side control can observe. Extended the parser with a Kotlin reader rather than leaving the obligation unnamed. It is a regex over `@Test fun \`...\``, and the direction it can be wrong in matters: a miss fails the manifest check loudly rather than passing it.
- 2026-10-23 (D2) — Verified both load-bearing tests fire rather than assuming they do. Converging the two removal message keys failed 2 of 4 refusal tests; making the child switch stop replacing failed the Back test. Both took about a minute. This unit's two test-first obligations were each written against criteria that a built-but-wrong implementation would have satisfied, so proving the assertion is reachable is part of writing it.

- 2026-10-24 (D3) — Wrote the decline tests before `void_accrued_cycles`, and the guardian-decline test failed against my own first implementation: it voided whatever seat it was handed, so calling it on a guardian decline would have cleared the student's debt. That is BR1.7's stated violation one layer below where this project last met it, on the presentation side. The function now re-reads `student_decision` itself rather than trusting the caller, on the team's own reasoning that a check above a query is one the next query can bypass — and it made the function idempotent for free, which the daily job needs. Test-first paid here exactly as the predicate predicts: the expected value was knowable from the rule and the wrong answer was a money error.
- 2026-10-24 (D3) — `FeeStateMapper` first derived `owesSomething` from `outstanding > Money.ZERO` and **did not compile**: the Kotlin `Money` value class exposes no comparison at all. The type refused the client-side arithmetic that `project.md` forbids in prose. Rewriting it to derive from the server's status enum is also more correct — a seat whose only period is waived has a zero balance and owes nothing, and the two derivations agree there by luck. A mechanical boundary caught in one compile what a reviewer might not have caught at all.

## Review findings
- 2026-10-24 (D3) — **The traceability sensor found two real defects, and neither was visible to the test suite.** The first traceability file declared 187 upstream ids and mapped 106; the other 81 were requirements this unit's own `nfr-requirements/` defines and I had never read against the code. - 2026-10-24 (D3) — Proved the verification guard fires rather than assuming it: with the row lock removed, **8 of 8** racing verifications are accepted and the 1000.00 claim is credited eight times. The project's standing rule is that a test which cannot fail is a defect in its own right, and a concurrency test is the shape where that is easiest to get wrong — the test passes either way until you check.
- 2026-10-24 (D3) — The conflict guard needed a `correcting` flag, and the reason is worth recording: FR9.2 makes every verification correctable, so the obvious guard — "refuse any verification of a decided claim" — passes the race test and silently breaks correction. Three existing correction tests would have failed, which is the only thing that would have caught it. A guard and a feature can be opposite readings of the same state, and the test that distinguishes them is the one to write first.
- 2026-10-24 (D3) — Seven of the 81 turned out to be inherited CITATIONS rather than ids D3 defines, and the `nfr-requirements/` files say so themselves in their own preamble ("A bare `NFR6.21` is a **citation** of D1's requirement, not an ID defined here"). - 2026-10-24 (D3) — The Kotlin ratchet printed 52.46% against a 52.54% floor and exited 0, which looked like a gate that cannot fail — this project's most-documented defect shape. It is not: the task carries a deliberate 0.5% tolerance with its reasoning in the source ("a ratchet that fires on 0.01% is a ratchet people disable"). Read the gate before reporting it broken.
