### Summary

The fix is complete and correct on all five points, and the rename is clean in source. Checked independently by reading the files rather than trusting the brief.

**Ordering.** `write_topic` calls `writable_session()` first, then `_existing_submission`, then the guarded `UPDATE`, matching `submit_roster` step for step. Security-design § 5.4 holds: the `TOPIC_VERSION_CONFLICT` raise re-reads `topic_version` only after authorization has already succeeded, and it carries no `current_state` at all, so even the roster disclosure shape the roster path has to guard against does not exist here.

**Replay lookup.** Both paths share one `_existing_submission`, which filters on `submitted_by_account_id` **and** `client_mutation_id` and on neither alone. A row found under the other `kind` is not silently returned: it raises `ConflictError("MUTATION_ID_ALREADY_USED")`, which is the right call — returning a topic version where a roster version was asked for would be a silent wrong answer.

**A replay writes nothing.** The `prior is not None` branch returns `TopicResult(topic_version=prior.resulting_version, ...)` and returns before the `sa.update` is constructed. No `topic_version` increment, no second `QueuedSubmission` row, so `created_at` cannot move. `tests/teaching/test_topic_replay.py::test_a_replayed_topic_write_leaves_created_at_unmoved` asserts it directly, and `..._does_not_apply_a_different_body` covers the nastier case of a replayed key carrying changed content.

**The constraints are as specified.** `uq_queued_submission_replay` is `(submitted_by_account_id, client_mutation_id)` — two columns, **not** scoped by `kind` — in both `migrations/versions/0006_teaching_and_recording.py` and `app/db/models.py`, with the reasoning stated identically in both. `uq_queued_submission_version` is `(session_id, kind, resulting_version)`, so the two counters cannot collide; `tests/teaching/test_topic_replay.py::test_a_roster_and_a_topic_write_reaching_version_one_both_succeed` proves that is not theoretical. `kind` is declared `sa.Column("kind", submission_kind, nullable=False)` with **no server default and no Python default** on either side.

**The rename is clean.** Across all source, test, Kotlin and schema files the only surviving `attendance_submission` tokens are `ix_attendance_submission_fk` in the migration and the model — and the reasoning holds on inspection, not merely on assertion: that index is created on the `attendance` table over `attendance.submission_id`, so its name describes the table it indexes. Renaming it would make the name less accurate. The remaining hits are upstream design prose from earlier stages, which this stage does not own; `security-design.md:413` is already with the human.

**Family reads.** `family_batch_view` resolves the seat through `readable_enrollment` before any query, and the guardian branch requires both `guardian_account_id == lens.account_id` **and** `guardian_decision == "accepted"` — so a named-but-never-agreed guardian is refused, which is the exposure the acceptance model exists to close. The attendance join is scoped by `Attendance.enrollment_id == enrollment_id` inside the join condition rather than in a filter above it, so a guardian sees their own child's presence and no other seat's. Refusal is byte-identical across all three cases: a missing row, a non-child row and a wrong-lens row all `raise refuse()` from the same shared constructor, so an invented id and a real-but-not-yours id are indistinguishable [BR7.2].

**The new error class is wired end to end.** `teaching.mutation_id.already_used` appears in `message-keys.json`, in `MessageKeys.kt`, and in both `values/strings.xml` and `values-bn/strings.xml` — so the cross-path refusal renders rather than falling through to a generic message on a Bangla-first screen.

The three new findings are all Minor and all of one kind: comments that narrate this stage's own review history rather than describing the code. None of them changes behaviour, and under an advisory pass they are the human's to weigh at the gate.
