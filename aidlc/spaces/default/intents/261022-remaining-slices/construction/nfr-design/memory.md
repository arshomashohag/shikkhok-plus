## Tradeoffs
<!-- example: 2026-05-29T10:14:32Z — picked TDD over BDD this run; the team is unit-first and the domain is well-understood -->

- 2026-10-23 — Refused a circuit breaker on the SMS gateway. The caller already fails fast (one attempt, no retry, a timeout recorded as `unknown` rather than `failed`) and the resource actually at risk is a budget, which the ceiling cascade protects per-scope. A breaker would put a second differently-shaped control over the same resource — opening on failure *rate* while the ceiling refuses on *count* — and reconciling them would mean deciding which is authoritative during an incident.
- 2026-10-23 — Recorded the staging outbox as a blast-radius fact in both security-design and logical-components. It hands an OTP to any caller and is kept out of production three independent ways; D1 adds a route that causes an OTP to be sent, so it widens what that outbox would expose if it ever ran there, while changing none of the three controls. The module's own docstring says "it is obviously fine" is the most expensive assumption available here, which is why it is written down rather than reasoned past.

- 2026-10-23 (D2) — Wrote that the schema-wide teacher-lens invariant "covers" the two new roster fields. "Covered" and "never on the list" are the same observable state and different guarantees. The design now says which one it has, and names the general obligation D2 inherits — a future personal field on this response must be added to the set, and the invariant will not notice if nobody does. That is exactly what D1 found when `address` needed BR3.4 to enrol it.

- 2026-10-23 (D2) — The centrepiece of this design is the one obligation with no server-side backstop: Back after a guardian switches child. - 2026-10-24 (D3) — **A true conclusion with the wrong citation propagated through three stages, and the coordinator started it.** I corrected the Functional Design's "OQ-4 resolves to nothing" by pointing at the prior record's `contract-design/contract-summary.md` § G — which POSES OQ-4 and explicitly leaves the owning Unit "latent", a Delivery Planning decision deliberately left open. The document that DECIDES it is this record's `units-generation/unit-of-work.md:134`, whose D3 scope line reads "Owns the FCM adapter per OQ-4". The conclusion — D3 owns the adapter, D4 consumes it — was right throughout. Only the source was wrong, and because I wrote it into two functional-design files, the NFR design copied it, and I then copied it again into a traceability entry while fixing an unrelated sensor failure. Four places, one unchecked citation. The distinction that matters: a document where a question is ASKED is not the document where it is ANSWERED, and "X is answered at Y" is a claim about Y that needs reading Y. Fixed in all four.
- 2026-10-24 (D3) — **A test specified as an equality would have failed against already-correct code.** The security design required "`AUTH_403_CODES` has exactly one resource-refusal code, asserted as an equality". That set holds two members today (`app/errors/codes.py:53`) and the second, `LENS_NOT_AVAILABLE`, is not an oracle — a lens-hint mismatch discloses nothing about whether a resource exists. Replaced with the narrower assertable property: `AUTH_403_CODES - ALLOWED_NON_RESOURCE == {NOT_AVAILABLE}`, pinning the non-resource members as a literal allowlist so a new 403 code fails the test until someone classifies it. Specifying a test is specifying code, and a specification that cannot pass is a defect in the design rather than work for the implementer.
- 2026-10-24 (D3) — **The absence-of-success alert was missing its commonest case.** The design covered a mid-run crash and overlapping runs but never said whether a run finding nothing due writes the heartbeat. Generation is monthly, so most days legitimately create nothing: writing only when `cycles_created > 0` would leave the row stale for weeks during correct operation, fire the 48-hour alert constantly, and get it muted — reaching the alert's own stated failure mode by the opposite route. The write is now unconditional on outcome and conditional only on completion, with "nothing was due" and "nothing ran" distinguished by a zero count against no advance at all.
