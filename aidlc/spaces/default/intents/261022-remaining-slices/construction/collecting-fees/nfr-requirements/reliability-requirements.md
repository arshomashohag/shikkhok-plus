# Reliability Requirements — D3 `collecting-fees`

**Stage**: nfr-requirements (3.2)
**Phase**: Construction
**Unit**: D3 `collecting-fees`
**Record**: 261022-remaining-slices

> **D3's reliability question is one nobody is watching.** Every failure mode
> before this unit had a person in front of a screen who would retry. The
> generation job runs at night, charges money, and has no user.
>
> The three questions that matter: what happens if it **fails mid-run**, if it
> **runs twice**, and if it **does not run for three days**. All three have
> answers, and all three answers are the same mechanism.

> **`NFRx.y` IDs are GLOBAL across units.** D3's start above the high-water
> mark each base had reached after D2: NFR18 from **.3**, NFR19 from **.8**.

## 1. Availability

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR18.3 | D3 states no availability target of its own and inherits the product's | Phase 1 is a single Lightsail host with a recreate-style deploy and an accepted short restart window | [team: Deployment] [NFR7] |
| NFR18.4 | **The generation job's availability requirement is daily, not continuous** | A missed run is recovered by the next run [BR1.4]. That is a materially weaker requirement than the API's and should not inherit the API's posture | [BR1.4] |
| NFR18.5 | Deploys carrying D3 are scheduled outside Bangladesh classroom hours, and **outside the generation window** | A recreate-style restart during generation kills a run mid-flight; NFR19.8 makes that survivable, but colliding deliberately is avoidable | [team: Deployment] [NFR20.22] |

**NFR18.4 is worth separating.** A fee view that fails is retried by a person
looking at the screen. A generation run that fails has nobody, and its
recovery is structural rather than human — which is exactly why the
self-healing property is a requirement and not a nicety.

## 2. The three job failure modes

Each is answered by the same mechanism — the unique constraint plus
`ON CONFLICT DO NOTHING`, with the `charge` appended only on a created row.

| Failure | What happens | Requirement |
|---|---|---|
| **Fails mid-run** | Enrollment-periods already committed stay committed; the rest are generated by the next day's run, which considers every period from the first generating one to the current | [NFR19.8] [BR1.4] |
| **Runs twice** | The second run's inserts conflict and do nothing; no second `charge` is appended | [NFR19.9] [BR1.3] |
| **Does not run for three days** | The next run considers three periods per enrollment instead of one and generates the missing ones. Note this is three *days*, which usually spans **zero or one** period boundary | [NFR19.10] [BR1.4] |

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.8 | Generation commits **per enrollment-period**, never as one transaction over the run | A partial failure then costs only the uncommitted remainder. One large transaction makes any failure total | [spec § 3.1 step 10] |
| NFR19.9 | Running the job any number of times on any number of days is **safe by construction**, not by a guard | The conflict is the success path and generation continues without raising | [BR1.3] [AC5.1.6] |
| NFR19.10 | The job considers **every period from the first generating one through the current**, not only the current | This is what makes a missed day heal rather than leave a permanent hole. Generating only the current period would silently never bill the gap | [spec § 3.1 step 3] [BR1.4] |
| NFR19.11 | The due-date clamp is **non-degrading**, so a re-run cannot change an answer the job already gave | A degrading clamp rewrites the anchor, making BR1.4's job non-idempotent across days. Anchor 31 gives 2027-02-28 then **2027-03-31**, not 2027-03-28 for ever | [BR2.2] [spec § 3.4] |

**NFR19.11 is a reliability requirement, not only a correctness one.** It is
the one place where a plausible implementation choice — clamping by writing
the clamped day back — breaks the self-healing property that the other three
requirements depend on. The two designs are separated by a computed case, and
the third row of the spec's table is the one that separates them.

## 3. Transactional integrity

The failures here do not lose rows; they lose *halves of pairs*, which is
worse, because the result is a ledger that balances wrongly rather than a
ledger that is missing something.

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.12 | A carry is written as a **pair in one transaction** — `carried_out` on the origin, `carry_forward` of equal amount on the receiver | A committed half is a manufactured or vanished obligation. `sum(carry_forward) == sum(carried_out)` holds structurally | [BR3.1] [spec § 2.3] |
| NFR19.13 | A verification's **claim decision and every ledger entry it produces** commit together | A committed decision with no entries is a teacher believing a payment was received that the balance does not reflect | [BR5.5] [FR6.7] |
| NFR19.14 | Over-approval's `receipt` and `credit_grant` commit together | Half of that pair is money that arrived and is recorded nowhere | [BR4.2] [spec § 5.4] |
| NFR19.15 | The `charge` and any `credit_apply` at generation commit together, in that order | Charge-then-apply in one transaction. Reversed, the credit computation sees zero owed and applies nothing | [BR4.5] |
| NFR19.16 | A decline's reversal — a `forgiveness` per outstanding cycle — is **appended, never written by deleting rows** | The ledger is append-only; the original `charge` stays. Deleting would make the balance correct and the history false | [BR1.6] [BR3.3] [spec § 4.1] |

## 4. Error classes

Retryability is a property of the error class, not a judgement at the call
site. D3 is the **first unit with declared error responses**, which closes a
known stopgap: `app/main.py` injects `ErrorEnvelope` into the generated schema
explicitly because FastAPI emits a component only when a route references one.
D3's declared responses turn that stopgap into a no-op rather than a lie — as
its own comment anticipates — and a ZAP pass driven from the schema can then
know which error shapes to expect.

| Condition | Class | Retryable | Requirement |
|---|---|---|---|
| Cycle exists for `(enrollment, period)` | *not an error* | — | The **success path** [NFR19.9] |
| Claimed amount zero or negative | `ValidationError` | no | Refused before recording [BR5.2] |
| No open cycle for a claim | `ValidationError` | no | Stated reason; **no cycle is created** to receive it [BR5.1] |
| Shortfall with no disposition chosen | `ValidationError` | no | The teacher must choose; a default silently picks between opposite outcomes [BR5.4] |
| Carry exceeding the origin's balance | `ValidationError` | no | Manufactured debt [BR3.2] |
| Negative ledger amount | `ValidationError` | no | The sign is in the kind [BR3.4] |
| Claim verified by a non-owning teacher | `AuthorizationError` | no | Lens check [NFR14.42] |
| Claim re-verified concurrently | `ConflictError` | no | Correction is a distinct path [NFR6.35] |
| Serialization failure in generation | `TransientError` | yes | Bounded transaction retry |
| Database connection failure | `TransientError` | yes | Fail fast |
| Push notification failure | *not surfaced* | — | Recorded as a `failed` event [NFR19.19] |

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.17 | Every D3 route **declares** its error responses in the OpenAPI schema | Closes the published-but-unreferenced envelope; the schema-diff gate keeps the committed copy current | [spec § 8] [team: Code Style] |
| NFR19.18 | Every envelope carries `code`, a server-provided `retryable` boolean, and `message_key` rather than `message` | A server-sent English string cannot be localized by the client in a Bangla-first UI | [team: Error handling] |

## 5. Notifications — best-effort, and what that does not excuse

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.19 | A push failure **never fails the operation that triggered it**, and is logged rather than surfaced | The project's stated exception to "silent failures are not acceptable" | [BR7.2] [FR10.2] |
| NFR19.20 | **The exception covers not surfacing, not failing to record.** The `ReminderEvent` row is written regardless of push outcome, carrying a failure `outcome` | That is precisely why a reminder is an event and not a boolean: a flag cannot express a failed send | [BR7.1] [FR10.3] |
| NFR19.21 | Dispatch happens **after the transaction commits**, outside it | A push for a write that then rolled back is worse than no push | [contract § D] |
| NFR19.22 | `UNREGISTERED` from FCM is **not an error** — it deletes the stored device token | It is the token-lifecycle signal; treating it as an error is how a dead-token table grows for ever | [D-42] [contract § D] |
| NFR19.23 | There is **no retry queue** for pushes in V1 | A reminder is re-sendable by a person; a queue would be a durability mechanism for the least durable thing in the product | [contract § D] |

**NFR19.22 is a shared property, not a D3-private one.** OQ-4 is answered at
`261016-shikhokplus-tuition-app/inception/contract-design/contract-summary.md`
§ G: the FCM adapter's owning Unit was latent between U6 and U7, whichever was
built first. U7 is D3's ancestor and U6 maps to **D4**, so **D3 owns the
adapter and D4 consumes the same one**. The failure OQ-4 names is two adapters
with two different `UNREGISTERED` behaviours — which is exactly what a second
adapter in D4 would produce.

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.24 | The adapter D3 builds is **shared infrastructure, and must be built as such** | D4 consumes it rather than reimplementing it. Its behaviours — best-effort, post-commit, `UNREGISTERED` deletes — belong to the adapter, not to the fee feature that happens to be its first caller | [OQ-4] [contract § G] |

## 6. Graceful degradation

| Dependency | Tier | Degradation |
|---|---|---|
| PostgreSQL | **Critical** | None. Every D3 path is a read of persisted rows or a write; there is nothing to degrade to. |
| The scheduler | **Not critical for correctness** | A missed run is recovered by the next [NFR19.10]. This is the one dependency whose failure is genuinely absorbed. |
| FCM | **Best-effort** | A failed push leaves a recorded failure event; the teacher can re-send [NFR19.20]. |
| SMS gateway | Not used by D3 | Reminders are push; D3 adds no gateway traffic. |

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.25 | **There is no offline path in D3.** Fee reads and every write require connectivity and fail with an explicit retry prompt | NFR5 permits offline writes for the **mid-class path only** — the topic log and attendance, which are D4's. A queued payment claim is a claim that may or may not exist | [NFR5] [TC-8] [D-9] |

## 7. The migration

| ID | Requirement | Target | Source |
|---|---|---|---|
| NFR19.26 | The migration is forward-only and backward-compatible, run as a distinct logged step before the new container serves traffic | Never as a side effect of application start | [team: Deployment] |
| NFR19.27 | A verified `pg_dump` to S3 precedes any production run, with object existence and non-trivial size asserted after upload | An unverified upload is not a backup | [team: Deployment] |
| NFR19.28 | The migration is rehearsed on staging before production | Four new tables is this record's largest schema change | [team: Deployment] |

**D3's migration is additive and low-risk, which is the unusual part.** It
creates four tables rather than altering existing ones, so the previous
application version continues to work against the new schema and a tag
rollback stays a valid rollback. **What a rollback does not undo is a
generated charge**: if the job runs and the release is then rolled back, the
cycles and ledger entries remain — correctly, since they record obligations
that were real. The ledger's append-only design means the remedy is a
compensating entry, never a delete [BR3.3].

## Assumptions & Open Questions

- **Assumed**: the existing post-deploy smoke set already covers D3's read
  path. The team practice names "one read of a fee cycle" as part of the smoke
  set — written before fee cycles existed, so D3 is where that line becomes
  executable rather than aspirational.
- **Assumed**: a `TransientError` in generation retries the single
  enrollment-period transaction rather than the whole run, consistent with
  NFR19.8's commit granularity.
- **Open, and not resolved here**: whether the generation job alerts on a
  failed run, and after how many consecutive failures. Treated in
  `observability-requirements.md` § 3, where the alert discipline that governs
  it already lives.
