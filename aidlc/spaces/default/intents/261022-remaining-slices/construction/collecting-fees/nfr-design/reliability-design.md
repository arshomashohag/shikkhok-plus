# Reliability Design — D3 `collecting-fees`

**Stage**: nfr-design (3.3)
**Phase**: Construction
**Unit**: D3 `collecting-fees`
**Record**: 261022-remaining-slices

> **Three questions, one mechanism.** What happens if the generation job fails
> mid-run, if it runs twice, and if it does not run for three days — all three
> are answered by the unique constraint with `ON CONFLICT DO NOTHING` and the
> charge appended only on a created row.
>
> The second half of this design is **transactional pairing**: the failures
> that matter here do not lose rows, they lose *halves of pairs*, which leaves
> a ledger that balances wrongly rather than one that is missing something.

## 1. Availability [NFR18.3, NFR18.4, NFR18.5]

| Requirement | Design |
|---|---|
| NFR18.3 | D3 states no availability target of its own. Phase 1 is a single host with a recreate-style deploy and an accepted short restart window |
| NFR18.4 | **The job's availability requirement is daily, not continuous.** A missed run is recovered by the next one, which is a materially weaker requirement than the API's and must not inherit the API's posture |
| NFR18.5 | Deploys carrying D3 are scheduled outside Bangladesh classroom hours **and outside the generation window** |

**NFR18.5's design is a scheduling constraint, and it is weak on purpose.**
A restart during generation kills a run mid-flight; § 2 makes that survivable,
so colliding is avoidable rather than dangerous. The mechanism is the human
choosing when to dispatch the deploy — deploys are explicitly dispatched, not
on merge [team: Deployment] — and **nothing automated prevents a deploy
landing inside the generation window.** Stated plainly: this obligation's
verifier is the person running the deploy.

## 2. The three job failure modes

| Failure | What happens | Requirement |
|---|---|---|
| **Fails mid-run** | Enrollment-periods already committed stay committed. The rest are generated by the next run, which considers every period from the first generating one through the current | NFR19.8, NFR19.10 |
| **Runs twice** | The second run's inserts conflict and do nothing; no second `charge` is appended | NFR19.9 |
| **Does not run for three days** | The next run considers the same periods and generates any missing. Three *days* usually spans **zero or one** period boundary | NFR19.10 |

### Commit granularity [NFR19.8]

**One transaction per `(enrollment, period)`**, never one over the run. A
partial failure then costs only the uncommitted remainder; one large
transaction makes any failure total, leaving the self-healing re-run more to
heal rather than less.

### Safe by construction, not by a guard [NFR19.9]

The conflict is the **success path**: generation continues without raising.
There is no "has this run?" check anywhere in the design, because such a check
passes a sequential test and fails with two workers
[`scalability-design.md` § 2.1].

### The period range is what makes a gap heal [NFR19.10]

The job considers **every period from the enrollment's first generating one
through the current**, not only the current. Generating only the current
period would silently never bill the gap — the hole would be permanent, and
nothing would report it, because every row that exists is correct.

### The clamp must be non-degrading [NFR19.11]

Due date is `day = min(anchor, days_in_month)`, **and the stored anchor is
never rewritten**.

Computed, anchor 31:

| Period | Days in month | Non-degrading (correct) | Degrading (wrong) |
|---|---|---|---|
| 2027-01 | 31 | 2027-01-31 | 2027-01-31 |
| 2027-02 | 28 | 2027-02-28 | 2027-02-28 |
| **2027-03** | 31 | **2027-03-31** | **2027-03-28** |
| 2028-02 | 29 | 2028-02-29 | 2028-02-28 |

**The third row separates the designs**, and the failure is a reliability one
rather than only a correctness one: a degrading clamp rewrites the anchor, so
re-running the job for an earlier period produces a *different* answer than
the first run gave. That breaks idempotency across days, which NFR19.9 and
NFR19.10 both depend on.

**The design's mechanism**: the clamp is a pure function of
`(anchor, period)`, and `Batch.fee_due_day` is read, never written, by the
generation path. A test asserts the computed table above, including the
2028-02 leap row.

## 3. Transactional pairing

Each of these is one transaction, and a committed half is worse than a
committed nothing.

| Requirement | Pair | What a committed half means |
|---|---|---|
| NFR19.12 | `carried_out` on the origin + `carry_forward` of equal amount on the receiver [BR3.1] | A manufactured or vanished obligation. `sum(carry_forward) == sum(carried_out)` holds **structurally** rather than by convention |
| NFR19.13 | The claim decision + every ledger entry it produces [BR5.5] | A teacher believing they approved a payment the balance does not reflect |
| NFR19.14 | Over-approval's `receipt` + `credit_grant` [BR4.2] | Money that arrived and is recorded nowhere |
| NFR19.15 | The `charge` + any `credit_apply`, **in that order** [BR4.5] | Reversed, the credit computation sees zero owed and applies nothing — a silent no-op |
| NFR19.16 | A decline's reversal: a `forgiveness` **per outstanding cycle**, appended [BR1.6] | — |

**NFR19.16 is the one with a tempting wrong implementation.** The reversal is
**appended, never written by deleting rows**: the original `charge` stays, and
a `forgiveness` of equal amount relieves it. Deleting would make the balance
correct and the history false — and the ledger's whole value is that it is
the audit trail [NFR24.9].

**The verifier for the pairing rules** is the enrollment-level invariant
already built: `derive()` plus the Hypothesis property test. A one-sided carry
is immediately visible as `sum(carry_forward) != sum(carried_out)`, which is
why the functional spec names the one-sided case as a computed figure — 1000
carried into a second 1000 charge reads **2000.00** two-sided and **3000.00**
one-sided.

## 4. Error classes — D3 adds none

**Retryability is a property of the class, not a judgement at the raise
site**, and this is mechanically true rather than a convention:
`app/errors/handler.py:63-80` reads `retryable` from the class "here and
nowhere else", and `app/schemas/errors.py:25-32` documents it as derived at
the handler. A raise site cannot set it.

**The class for a fee refusal is already decided**, in a docstring written
before fees existed (`app/errors/_classes.py:108-113`):

> **Valid request; current state forbids it. Refetch and decide.**
> Retrying as-is is wrong, which is why a cost-ceiling or **balance refusal**
> is this class and never `TransientError`.

So a payment claim refused because the balance moved is a `ConflictError`, and
the client **refetches rather than retries**. That settles a question which
would otherwise look open.

### D3's failures, mapped to the five existing classes

| Condition | Class | Retryable | Note |
|---|---|---|---|
| Cycle exists for `(enrollment, period)` | *not an error* | — | The **success path** under `ON CONFLICT DO NOTHING` [NFR19.9] |
| Claimed amount zero or negative | `ValidationError` | no | Refused before the claim is recorded [BR5.2] |
| No open cycle for a claim | `ValidationError` | no | Stated reason; **no cycle is created** to receive it [BR5.1] |
| Shortfall with no disposition chosen | `ValidationError` | no | A default would silently pick between opposite outcomes [BR5.4] |
| Carry exceeding the origin's balance | `ValidationError` | no | Manufactured debt [BR3.2] |
| Negative ledger amount | `ValidationError` | no | The sign is in the kind [BR3.4] |
| Claim verified by a non-owning teacher | `AuthorizationError` | no | Lens check; the **shared** code [NFR14.42, `security-design.md` § 4] |
| Fee cycle or claim absent, or not the caller's | `AuthorizationError` | no | 404 where a 403 would disclose existence; the shared code |
| Claim re-verified concurrently | `ConflictError` | no | Correction is a distinct path [NFR6.35, BR5.7] |
| Balance moved under a claim | `ConflictError` | no | The class the docstring above names explicitly |
| Serialization failure in generation | `TransientError` | yes | A bounded retry of **that one** enrollment-period transaction |
| Database connection failure | `TransientError` | yes | Fail fast |
| Push notification failure | *not surfaced* | — | Recorded as a `failed` event [NFR19.19, NFR19.20] |

**Every row maps to one of the five. D3 adds no sixth class, and no new
retryability judgement.** I looked for a D3 failure fitting none of the five
and did not find one: the closest candidate is "generation partially
completed", which is not an error at all — it is the committed prefix, and the
next run continues from it.

### The database's three cases, following the per-boundary rule

The team's error-handling practice already states the database split, and the
design follows it rather than restating it differently:

- an `(enrollment_id, period)` constraint violation is **the success path**;
- a serialization failure is a **bounded transaction retry**;
- a connection failure **fails fast**.

### Declared responses [NFR19.17, NFR19.18]

**D3 is the first unit with declared error responses**, which closes a known
stopgap: `app/main.py:144-182` injects `ErrorEnvelope` into the generated
schema explicitly, because FastAPI emits a component only when a route
references it. The code says it is a stopgap. **D3's declared responses turn
it into a no-op rather than a lie**, as its own comment anticipates — and a
ZAP pass driven from the committed schema can then know which error shapes to
expect.

Every envelope carries `code`, the server-provided `retryable` boolean, and
`message_key` rather than `message` — a server-sent English string cannot be
localized by the client in a Bangla-first UI.

**The verifier is the schema-diff gate, which already exists**: the committed
`openapi.json` must match the generated one, so a route declaring no error
responses shows as a reviewable diff.

## 5. Notifications [NFR19.19–NFR19.24]

| Requirement | Design |
|---|---|
| NFR19.19 | A push failure **never fails the operation that triggered it**, and is logged rather than surfaced — the project's stated exception to "silent failures are not acceptable" |
| NFR19.20 | **The exception covers not surfacing, not failing to record.** The `ReminderEvent` row is written **regardless of push outcome**, carrying a failure `outcome` |
| NFR19.21 | Dispatch happens **after the transaction commits**, outside it. A push for a write that then rolled back is worse than no push |
| NFR19.22 | `UNREGISTERED` from FCM is **not an error** — it deletes the stored device token. It is the token-lifecycle signal, and treating it as an error is how a dead-token table grows for ever |
| NFR19.23 | **No retry queue** in V1. A reminder is re-sendable by a person; a queue would be a durability mechanism for the least durable thing in the product |

**NFR19.20 is the requirement that shapes the write order**, and the order is
the opposite of the intuitive one:

```
COMMIT the reminder event (outcome = 'pending')
dispatch the push                                  ← outside the transaction
UPDATE the event's outcome to 'sent' or 'failed'
```

Writing the event *after* a successful dispatch would mean a crash between
dispatch and write loses the record of a send that happened — and the whole
reason a reminder is an event rather than a boolean is that a flag cannot
express a failed send.

### The adapter is shared infrastructure [NFR19.24]

**Two documents say different things, and only one of them decides.**

`261016-shikhokplus-tuition-app/inception/contract-design/contract-summary.md`
§ G **poses** OQ-4 and leaves it open: the adapter's owning Unit is "latent —
U6 or U7, whichever is built first", explicitly a Delivery Planning
sequencing decision, because the dependency artifact deliberately declined a
`U6 -> U7` edge rather than lose a parallel set. It states the stake — "left
unrecorded it becomes two adapters with two different `UNREGISTERED`
behaviours" — and chooses nothing.

**This record's `inception/units-generation/unit-of-work.md:134` is what
decides it**, assigning the adapter to D3 in D3's own scope line: "Owns the
FCM adapter per OQ-4." U7 is D3's ancestor and U6 maps forward to D4, so the
latency resolved the way the sequencing settled it: **D3 owns the adapter and
D4 consumes the same one.**

The conclusion is unchanged; the citation is. An earlier draft of this
section cited § G as the thing that answered OQ-4, which it does not — it is
where the question is asked. The distinction matters because a reader
following that citation would find an open question and reasonably conclude
the design had decided something it had no authority to decide.

| Decision | Detail |
|---|---|
| **Placement** | Beside the SMS gateway client, **not** inside the fee feature that happens to be its first caller |
| **Why placement follows from ownership** | An adapter living in `feature/fees` is one D4 will copy rather than import — which produces exactly the two-adapter outcome OQ-4 exists to prevent: two different `UNREGISTERED` behaviours |
| **What belongs to the adapter** | Best-effort, post-commit, failure logged and not surfaced, `UNREGISTERED` deletes the token, no device or advertising identifier [NFR11.2] |
| **What belongs to the caller** | The decision to send, and the `ReminderEvent` row |

**The verifier that D4 does not build a second one** is an import-boundary
check in the same shape as the money module's: no module under a feature
package may define an FCM client. That is **new work in D3** and is named here
because, absent it, OQ-4's failure mode is prevented only by D4's author
remembering.

## 6. The scheduler — designed so either choice holds

**The choice is the human's** [tech-stack § 2]: a host-level cron entry
invoking a management command, or in-process (APScheduler) inside the API
container. The requirements are stated **against the job, not its scheduler**
— NFR6.39, NFR25.9 and NFR26.3 — and this design keeps them that way.

### What holds either way

| Property | Why it is scheduler-independent |
|---|---|
| Correctness under double-firing, overlap and missed days | §§ 2 and `scalability-design.md` § 2. The constraint is the lock |
| The job is a management command taking no required arguments | Runnable by hand under either option, which is the recovery procedure for NFR25.9 |
| The heartbeat row (`observability-design.md` § 3) | Written **by the job**, so it records that the work ran, not that a timer fired |
| The absence-of-success alert | Queries the heartbeat, so it detects silence whatever caused it |
| Commit granularity, retry class, pairing | All inside the job |

### What differs, stated so the human can choose

| | Host-level cron | In-process (APScheduler) |
|---|---|---|
| **"Did it run?" answerable from outside the app** | Yes — an exit status and a log line outside the application's own logs | **No** — the evidence is the application's own logs, which is circular for NFR25.9 |
| **Runnable by hand** | Yes, the same command | No handle; a person must trigger it some other way |
| **Survives a deploy** | **Only if installed by `user_data.sh.tftpl`** — see below | Yes, it ships with the image |
| **Fires per worker** | Once | **Once per worker.** Harmless here (the constraint absorbs it) but it makes the skipped-by-conflict metric [NFR25.13] read non-zero every day, which costs that metric its meaning |
| **New operational surface** | One line of Terraform-managed host configuration | None outside the container |

**The constraint on the cron option is not optional.** The instance is
**replaced on every deploy**: `deploy.yml`'s rollout step refreshes the ASG so
the new instance re-runs `user_data`, deliberately — "a refresh exercises the
same path a replacement takes after a failure." So *a host-level cron entry*
means **an entry installed by `user_data.sh.tftpl`, not one added by a person
over SSM.** A hand-added entry is wiped by the next routine deploy, and
because generation self-heals, nothing looks wrong until nobody has been
billed since that deploy.

**If the in-process option is chosen, one design element changes**: the
skipped-by-conflict metric must be read per worker rather than as a run total,
or NFR25.13's "a sustained non-zero is a double-scheduling bug" signal is lost
to the normal case. That is the only change; everything else in this file and
in `observability-design.md` holds unmodified.

## 7. Graceful degradation

| Dependency | Tier | Degradation |
|---|---|---|
| PostgreSQL | **Critical** | **None.** Every D3 path is a read of persisted rows or a write; there is nothing to degrade to |
| The scheduler | **Not critical for correctness** | A missed run is recovered by the next [NFR19.10]. The one dependency whose failure is genuinely absorbed |
| FCM | **Best-effort** | A failed push leaves a recorded failure event; the teacher re-sends [NFR19.20] |
| SMS gateway | Not used by D3 | Reminders are push; D3 adds no gateway traffic |

**No circuit breaker on FCM, and the reason is the same one D1 recorded for
the SMS gateway.** The caller already fails fast and absorbs the failure
completely — the operation commits regardless, the outcome is recorded, and a
person re-sends. A breaker would add a second control with no behaviour to
change: there is no fallback to open onto, and no cost being protected.

**No offline path** [NFR19.25]. Fee reads and every write require connectivity
and fail with an explicit retry prompt. NFR5 permits offline writes for the
**mid-class path only** — the topic log and attendance, which are D4's. A
queued payment claim is a claim that may or may not exist, which is the worst
shape available for a money record.

## 8. The migration [NFR19.26, NFR19.27, NFR19.28]

| Requirement | Design |
|---|---|
| NFR19.26 | Forward-only and backward-compatible, run as a **distinct logged step** before the new container serves traffic — never as a side effect of application start. Built: `deploy.yml` runs Alembic as its own step after a plan job that prints what is about to be applied |
| NFR19.27 | A verified `pg_dump` to S3 **precedes** any production run, with object existence and non-trivial size asserted after upload. An unverified upload is not a backup |
| NFR19.28 | Rehearsed on staging first. Four new tables is this record's largest schema change |

**D3's migration is additive and low-risk, which is the unusual part.** It
creates four tables rather than altering existing ones, so the previous
application version continues to work against the new schema and a tag
rollback stays a valid rollback.

**What a rollback does not undo is a generated charge.** If the job runs and
the release is then rolled back, the cycles and ledger entries remain —
correctly, because they record obligations that were real. The ledger's
append-only design means the remedy is a **compensating entry, never a
delete** [BR3.3].

**One migration ordering note**: the narrowed `ledger_entry` grant of
`security-design.md` § 5 is issued in the same migration that creates the
table, after the `CREATE TABLE`. Issued earlier it names a table that does not
exist; issued in a later migration it leaves a window in which the blanket
grant from `0001` applies.

## Assumptions & Open Questions

- **Assumed**: the existing post-deploy smoke set already covers D3's read
  path. The team practice names "one read of a fee cycle" as part of the smoke
  set — written before fee cycles existed, so **D3 is where that line becomes
  executable rather than aspirational**.
- **Assumed**: a `TransientError` in generation retries the single
  enrollment-period transaction rather than the whole run, consistent with
  NFR19.8's commit granularity. The retry is bounded — three attempts — and a
  final failure counts toward NFR25.10's per-enrollment failure metric rather
  than aborting the run.
- **Assumed**: the job takes the current date as a parameter defaulting to
  today, so the across-days test injects time rather than patching a clock.
- **Open, and the human's**: the scheduler choice in § 6. Everything in this
  design holds under either, and the one element that changes is named.
